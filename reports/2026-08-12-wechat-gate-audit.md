# 岸岸微信小程序功能闭环与兼容性审计

> 审计日期：2026-08-12  
> 代码基线：`main@d42761ce4485`，审计时工作区有 108 项未提交变更  
> 用户确认原则：做出来的功能必须有用、完整串联；接口兼容问题不得留给用户点击后发现  
> 性质：当前代码事实与交付标准，不是上线完成报告

## 1. 正确的问题定义

问题不是“需不需要更多门禁”，也不是“报错后给什么兜底”。

真正的问题是：项目里页面和功能很多，但部分能力只完成了自己这一层，没有证明整个链路兼容：

```text
可见入口
  -> 页面事件
  -> 路由与参数
  -> 生成 API 客户端
  -> 后端契约与权限
  -> 数据、内容或 AI 依赖
  -> 真实结果写入
  -> 下一环读取并改变用户动作
```

任何一段对不上，都是开发未完成，不是合理的用户状态。不能等用户点击后才暴露接口不兼容、页面不在白名单、provider/release 未配置、任务路由不匹配或题库契约失败，再用“暂不可用”掩盖。

正式交付原则：

> **可见功能必须有用；点击必须走通；结果必须进入下一环。**

运行时兜底只处理网络、超时和临时服务故障。稳定复现的 403、404、409、422、500、503 或固定配置不匹配必须修复原链路。

## 2. 本轮接线结果

### 2.1 四种冷启动入口已不再乱跳旧表单

2026-08-12 已完成第一批确定性接线修复：

- 成绩单进入正式 OCR、字段确认和外部模考确认链；后端写入 `learning.score_evidence`，学习脑读取 `scoreEvidenceCount`；
- 错题进入题图结构化、题目匹配、学习包和真实答卷确认链；后端写入 `learning.external_answer_facts`，学习脑读取 `externalAnswerCount`；
- 快速诊断先读取正式今日计划，只接受后端生成且带当前 `planTaskId` 的 `objective_baseline` 任务；候选任务损坏时会继续寻找后续合法任务，不再拿旧备考经历页冒充诊断，偶发失败只向用户提供保留选择后的重试提示并把技术原因留在日志；
- “还没选岗”进入正式岗位偏好页，确认地区和岗位层级后写入后端版本，并标记本次入口已获得岗位偏好证据；
- 四个入口加载期间禁止重复触发，避免重复命令和多次跳转。

这不等于四条黄金链已经全部上线验收。成绩单和错题还需补“证据进入画像后，今日任务确实变化”的真实数据库 journey；岗位偏好仍需继续形成目标岗位/目标分；快速诊断仍依赖当前计划能为新用户产生基线任务。

### 2.2 今日任务的前后端路由契约已加联合检查

后端计划产生 `startUrl`；前端随后校验注册路由、任务类型、`planTaskId`、stage、mode 和查询参数。任一生产者与消费者约定不一致，页面会把任务设为不可打开并显示“任务入口没生成好”。

本轮新增了跨端契约测试，确保后端会补 `planTaskId` 的三类任务路由都存在于小程序注册表，并保留前端对 `mode`、`stage`、任务归属和参数唯一性的校验。相关测试通过。

尚缺的证据是：真实测试账号获取今日计划后，逐个点击并创建实际训练会话、进入第一题、完成后回写计划。这仍是下一轮 journey test，不因静态契约通过而宣称完成。

### 2.3 AI 功能存在多处独立兼容点

岸岸问答及其他 AI 能力可能同时依赖：

- 页面、workspace 和 object type 白名单；
- AI 场景、prompt、schema 和评测套件身份；
- provider/model/release 配置；
- 真实用户外部处理授权；
- 权益和配额；
- 前端语义状态映射。

这些内部控制可以保留，但入口发布前必须作为一个整体对齐。页面显示“问岸岸”后才返回 `page_not_allowlisted`、`release_not_approved` 或长期 503，属于功能未交付，不属于正常降级。本轮已把所有直接发起“问岸岸”的前端 `routeId` 与后端页面权限清单加入同一项自动测试，防止页面新增后漏配白名单。

当前 `.product-governance/ai-scenarios.json` 为空，而运行时代码已有多个场景，也说明机器治理清单与运行实现没有统一来源。

### 2.4 题库与结构化图片必须接到真实作答

题库交付会检查题量、答案、冻结内容版本和视觉资产。检查本身必要，但完整功能应在任务展示前完成可用题组选择。当前运行时仍可能因题量不足、视觉题缺少已发布图片或答案键异常返回 503。

图片结构化也不能以“识别 payload 已生成”为完成。它必须在实际做题页正确渲染，参与作答、错因、解析、同类题和后续选题，才能算真正有用。

### 2.5 局部测试通过不等于功能通过

`apps/wechat` 的全量 `npm run check` 已通过，包括 61 页结构与交互覆盖、15 个分包、1050 个 Vitest 测试和 9 个云函数测试。但现有四路径测试主要检查模板文案、按钮绑定、路由函数和 local storage；大量 controller 测试使用 mock API。

这些测试能保护局部代码，却不能证明一个真实入口穿过生成客户端、后端、数据库/内容/AI，再回到下一页面。以后不能用“按钮存在、接口单测绿、全量 check 绿”宣称该功能有用。

## 3. 功能完成的强制定义

每个用户可见功能必须同时证明：

1. **入口真实**：页面展示条件与环境实际能力一致，不展示永远失败的按钮；
2. **接口兼容**：路由参数、OpenAPI、生成客户端、后端 schema、enum 和错误语义完全一致；
3. **权限兼容**：账号归属、页面上下文、AI 场景和数据权限在目标环境预配置并通过；
4. **依赖就绪**：所需题库、图片、方法卡、provider 和 release 不是只有代码声明，而有当前版本数据；
5. **命令成功**：真实点击可以完成业务写入，并处理幂等、冲突和恢复；
6. **结果有用**：结果不是孤立候选、本地状态或终点报告，至少改变一个后续任务、判断、复测、能力或岗位动作；
7. **用户看见因果**：岸岸说明“因为刚才发生了什么，所以现在变成了什么”；
8. **端到端证据**：测试从真实入口开始，验证到下一环消费，不以单层 mock 代替。

缺一项，功能状态就是“未完成”，不允许写成“已交付但暂不可用”。

## 6. 接口兼容性验收

每条功能链需要一项真正的 journey test：

- 使用当前 OpenAPI 生成的客户端，不手写一个“看起来一样”的 mock；
- 启动真实后端和测试数据库，装入与发布一致的最小题库、视觉资产和 AI 配置；
- 从页面事件或等价入口调用开始；
- 断言没有稳定复现的 403/404/409/422/500/503；
- 断言规范事实确实写入；
- 断言下一消费者可以读到并改变下一个动作；
- 记录 request ID、功能 ID、输入/输出契约版本，失败能定位到具体边界。

AI 外部调用可以使用契约级假 provider，但页面权限、场景身份、release、配额、请求/响应 schema 和结果交接必须走真实代码，不能全部 mock 掉。

## 7. 后续修复顺序

### F1：建立“可见功能清单”

从 61 个页面和所有可见按钮提取稳定功能 ID，记录入口、用户价值、后端命令、依赖、规范写入和下一消费者。找不到下一消费者的功能先标为半闭环。

### F2：优先修黄金链路接口

先修四种冷启动、今日主任务、错因、图片结构化和岸岸反馈，不继续新增页面。每条必须从点击走到下一环。

### F3：修 AI 和权限联合兼容

把页面权限、AI 场景、provider/release、权益和前端语义作为同一个发布检查；不再让各层分别通过、组合起来却报错。

### F4：补真实 journey tests

测试失败直接说明功能未完成。局部单测继续保留，但不能替代功能验收。

### F5：再接 teach-back

只有上游补弱、真实作答和下游掌握/复测已经走通后，才接“讲给岸岸”。否则它又会成为一个孤立的新功能。

## 8. 与门禁和兜底的边界

- **开发/发布检查**：接口、schema、权限、AI release、题库和下一环兼容。失败就修，不发布半成品入口。
- **正常业务边界**：例如没有资格证据时不下资格结论、用户未确认候选时不写成事实。这保护结论真实性，但不能表现成莫名其妙的接口错误。
- **运行时恢复**：网络断开、超时、进程退出等偶发故障，允许保存草稿、重试和恢复。
- **禁止的伪兜底**：稳定接口不兼容时换一个无关功能、返回泛化“暂不可用”、生成假数据或把半成品称为降级体验。

最终目标不是一个“永不报错但没什么用”的系统，而是一个功能少一点也没关系、每个功能都真的有用且相互接得上的系统。
