## 一、为什么需要中控大脑

今天的核实结论:**系统"会学",但"不会自己决定怎么学"。** 现在是"伪中枢三件套":
- `planning` 排题(规则权重,读原始掌握度,不吃大脑)
- `cause_agent` 归因(解释为什么错)
- `learning_brain` 记账(只读汇总,不决策)
- `companion`(岸岸)只读它们,转译成对话

**没有一个人能说:"因为你 A 弱 + B 错因 + 离目标差 D 分,所以下一步做 E。"** 中控大脑就是补上这个"人"。

---

## 二、中控大脑是什么(一句话)

> **一个会读全部学习状态、主动推断"下一步该怎么学"、并驱动确定性计划引擎的决策层。**
> 它用 agent 做"理解与推断",但执行仍是确定性的(计划引擎),既灵活又可复现。

它不是替代 planning,是**在 planning 之上加一层"为什么"**。

---

## 三、它读什么(输入)

中控大脑的输入,是**阶段 1 已接通的全部状态** + learning_brain 的聚合:

| 输入 | 来源 | 状态 |
|---|---|---|
| 目标分数 + 差距 | position_decision / target_scores | ✅ 已有 |
| 能力估计(版本化) | ability_estimation | ✅ 阶段1接通内场模考 |
| 已确认错因(近14天) | cause_agent → confirmed_cause_versions | ✅ 阶段1接通选题 |
| 知识树薄弱点 | learning_brain _knowledge_point_weaknesses | ✅ 已有(只读) |
| 每日任务生成 | planning engine/candidates | ✅ 阶段1完成 |
| 申论掌握状态 | essay_intelligence mastery | ✅ 已有 |
| 完成度/耗时/放弃 | real_attempt 过程证据 | ✅ 已有 |
| 学习偏好/可用时间 | onboarding / capacity | ✅ 已有 |

**关键**:这些输入**全部真实存在、能读到**,中控大脑不需要造新数据,只需要"读 + 推断"。

## 四、它产出什么(核心:决策)

中控大脑的核心产出是 **"下一步策略"**——不是直接改计划,而是告诉计划引擎**"这周该侧重什么"**。产出的形态建议是**策略指令**:

```
策略指令示例:
{
  "focus": "行测-数量关系",            // 本周侧重的薄弱
  "cause_direction": "计算",           // 针对的错因方向
  "essay_emphasis": "作答-评阅",       // 申论侧重
  "mock_schedule": "周三一次模考",       // 模考安排
  "rationale": "数量关系正确率仅42%，近14天错因集中在计算，距目标差15分"  // 人话解释
}
```

**设计原则(关键)**:
- 中控大脑产出的是**"策略意图"**,不是**"具体任务清单"**
- 具体任务仍由计划引擎(确定性)排——**策略决定"侧重什么",引擎决定"排哪些"**
- 这样:agent 负责"理解与选方向"(灵活),引擎负责"可复现执行"(稳定)

## 五、怎么驱动计划(输出接入点)

中控大脑的决策要能影响计划。现在 planning 有个**天然的接入点**——`active_strategy_decisions` 表(策略决策),它已经是 planning 的输入之一。但它是**用户手填**的(`create_strategy_candidate` 只有用户从 ability-module 页提交)。

**建议**:让中控大脑成为 `strategy_candidate` 的**新生产者**。现在这个表有 `producer_type=rule|agent` 字段**从无生产者**,中控大脑正好补上:

```
中控大脑(agent) → 推断策略 → 写入 strategy_candidate(producer_type=agent)
  → planning 读 active_strategy_decisions → 影响排题
```

这样:
- **不新造机制**(复用已有的策略决策表)
- **用户仍是最终裁决**(策略候选要用户确认,符合"先预览再确认"哲学)
- **可追溯**(策略有版本、有指纹、有 rationale)

## 六、岸岸怎么对话(交互层)

岸岸是中控大脑的"嘴"。用户问"为什么这么排""我想改",岸岸代表大脑回答:

**用户 → 岸岸 → 中控大脑**:
- "为什么今天排这么多数量?" → 岸岸读大脑的 rationale:"因为数量正确率 42%、近 14 天错因集中在计算、距目标差 15 分,所以这周侧重数量"
- "我今晚只能学 1 小时,减点行测" → 岸岸→中控大脑→改容量(阶段 1 已完成:岸岸→plan→capacity 已通)
- "我觉得我的薄弱不是数量,是资料" → 用户裁决,更新大脑的策略

**中控大脑 → 岸岸 → 用户**:
- 大脑推断出"该练资料分析了",岸岸主动提示:"我注意到你资料分析连续 3 次没练了,这周要不要排一次?"(大脑主动→岸岸→用户确认)

## 七、实现形态(怎么落地)

**建议:不是新建一个大域,而是给现有域加一个"决策模块"。**

```
backend/app/domains/learning_brain/       (已有的"账本")
  └── agent.py   ← 新增:中控大脑决策 agent(读状态 → 推断策略)
  └── 复用 strategy_candidate 表作为输出
```

具体:
1. **新增 `learning_brain/agent.py`**:一个 LLM agent,输入是 learning_brain profile + 目标 + 错因 + 能力(全部已能读到),输出是"策略指令"(上面的 JSON)
2. **输出接 `create_strategy_candidate`**:策略指令变成 strategy_candidate(producer_type=agent),走已有的确认流程
3. **planning 已能读 active_strategy_decisions**:策略确认后自然影响排题
4. **岸岸接入**:`_context_payload` 已注入 learningBrain,岸岸已能读策略;补"岸岸主动提示策略"的入口

**关键**:agent 只产出**策略意图**(结构化 JSON + rationale),不直接改任务、不改排题。确定性永远在 planning。

## 九、风险与边界(诚实)

1. **agent 不可复现**:策略是 agent 推断的,同样输入可能产出不同策略。缓解:策略指令 + rationale 落库(可追溯),且只影响"侧重",不影响"确定性排题"
2. **策略何时触发**:不能每次对话都重算策略(贵)。建议:策略**按需/定期**重算(比如每天首次进 app、或错因确认后),不是实时
3. **用户裁决是关键**:agent 策略只是"候选",用户确认才生效(复用 strategy_candidate 的确认流程)
4. **首次无数据**:新用户没有错因/能力历史,大脑只能说"数据不足,先建立基线"(learning_brain 已有此逻辑)
5. **过度个性化风险**:大脑可能把用户带偏(比如只练一个模块)。缓解:策略指令里加"均衡约束"(如行测申论都要覆盖)

## 十、待产品负责人拍板的问题

1. **策略粒度**:策略指令是"周级"(本周侧重)还是"天级"(每天侧重)?建议周级(稳定,不频繁变)
2. **主动 vs 被动**:大脑是"用户问才答"(被动)还是"主动提示"(如"该练资料分析了")?建议先被动,后加主动
3. **策略触发时机**:每天首次进 app?错因确认后?建议:错因确认后 + 每天首次
4. **用户能改策略吗**:用户能直接改大脑的策略吗(比如"我觉得侧重错了")?建议:能,用户裁决权最高
5. **要不要展示 rationale**:用户看到"为什么这样排"吗?建议:展示(这是信任的关键)
