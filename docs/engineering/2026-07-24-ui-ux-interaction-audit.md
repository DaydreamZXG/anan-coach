# 岸岸小程序 UI、UX 与交互深度审计

日期：2026-07-24  
审计对象：`apps/wechat` 微信小程序与本地 Figma Design File 交付包  
审计性质：源码级只读审计；本轮未修改任何产品 UI、路由、接口或业务逻辑

## 1. 结论

当前小程序不能认定为“Design File 已完整复刻”，也不适合直接把现状交给下一个模型继续自由补页面。

更准确的状态是：

> **核心页面已大量接入真实业务，但视觉系统没有真正以 Design File 为代码权威；58 个注册页面中只有 30 个拥有本版 Figma 基线，关键闭环仍存在视觉完成、交互未完成的情况。**

本次审计与功能生产审计相互独立：

- 功能、接口、数据与生产闭环见：[2026-07-24-figma-production-audit.md](./2026-07-24-figma-production-audit.md)
- 本文只回答：
  - 页面是否忠实于 Design File；
  - 信息层级是否清楚；
  - 用户是否知道下一步做什么；
  - 点击后是否得到符合预期的结果；
  - 岸岸是否真正贯穿学习上下文；
  - 手机、平板、动效、触控与可访问性是否达到可发布水平。

## 3. 现有测试不能证明 UI/UX 已完成

### 3.1 视觉覆盖测试只证明“页面被列入清单”

`apps/wechat/scripts/validate-visual-coverage.mjs` 的核心逻辑是：

- 读取视觉场景的路由；
- 确认路由已注册；
- 确认 58 个注册页面都至少出现在一个场景里。

它不验证：

- 页面是否与 Figma 同源；
- 排版、字号、留白、Logo、颜色是否一致；
- 设计状态是否全部实现；
- 页面是否仍在使用旧设计系统。

### 3.2 交互覆盖测试只验证一个主按钮

`apps/wechat/scripts/validate-interaction-coverage.mjs` 为每个页面验证一个 `primaryInteraction`：

- WXML 中存在选择器；
- WXML 绑定了处理函数；
- 控制器里存在同名方法。

它不真正点击，也不验证：

- 点击后的页面是否正确；
- 次级动作是否有效；
- 表单、弹层、返回、取消和重试是否完整；
- 状态机是否走到正确结果；
- 用户是否理解动作后果。

因此“58 个页面都有交互合同”不能等同于“58 个页面均可用”。

## 4. 发布阻断级 UI/UX 问题

### UX-P0-01：Design File 没有成为运行时代码权威

证据：

- 运行时没有导入 `design-file.tokens.wxss`；
- `design-system/tokens/index.wxss`、`app.wxss`、`primitives/index.wxss` 和多套 `page-shell.wxss` 同时定义颜色、卡片、按钮与页面；
- `.page`、`.card` 等通用类被多次定义，并受导入顺序覆盖；
- Design File 的主色是 `#615fff`，但运行时仍大量使用旧青色、蓝色与橙色；
- Design File Logo 是黑色线性脑形 SVG，当前登录页和岸岸页使用的是另一枚渐变栅格 Logo。

用户后续看到的“像 Figma”和“不像 Figma”将取决于局部 CSS 覆盖顺序，而不是稳定的设计系统。

发布门槛：

- 建立唯一运行时令牌入口；
- 为 Design File 素材建立明确映射清单；
- 删除同语义的重复全局类；
- 设计稿规定的 Logo、图标和背景必须使用可追踪素材。

### UX-P0-02：28 个注册页面没有本版 Design File 基线

45 个 Figma 状态只覆盖 30 个独立路由。其余 28 个页面即便可以打开，也不能据此声称“全量 UI 已接入”。

更严重的是，核心页面会跳入这些旧视觉页面：

- 能力页进入 `ability-module`、`error-pattern`；
- 我的页进入通用报告中心；
- 申论主流程进入旧 workbench 页面；
- 行测任务入口、模考和报告仍有另一套视觉；
- 设置、隐私、资格和通知又是不同风格。

这会让用户感觉自己在多个产品之间跳转。

发布门槛：

- 为高频且对用户可见的无基线路由补正式设计；
- 暂不开放的路由从入口移除，而不是暴露半成品；
- 不允许以“页面能打开”代替设计验收。

### UX-P0-03：登录页的同意状态不真实

当前登录页展示了一个静态勾选效果，但用户不能：

- 主动勾选或取消；
- 打开用户协议；
- 打开隐私政策；
- 明确确认自己同意的内容。

这不仅是交互问题，也会降低首次登录信任感。页面不能用装饰性勾选假装用户已经做过选择。

发布门槛：

- 协议与隐私政策可打开；
- 同意状态可操作且与登录动作一致；
- 登录按钮的可用状态与同意状态一致；
- 文案不能暗示未发生的用户授权。

### UX-P0-04：岸岸没有真正进入做题上下文

产品定位要求岸岸是备考总控台，不是普通聊天框，并能与做题中的画词、疑问和动作联动。

当前情况：

- 岸岸 Tab 的总控台结构已存在；
- 做题页工具按钮标记为“打开岸岸与做题工具”；
- 实际打开的工具只有标记、争议、帮助、护眼、字号等；
- 材料阅读器只有缩放、字号和护眼；
- 回答过程中不能对选中文字追问；
- 不能把当前题目、材料片段、排除轨迹和草稿作为上下文交给岸岸；
- 练习完成后才能从部分结果状态进入岸岸。

这会造成品牌承诺与实际能力之间的断裂，用户仍会把岸岸理解为另一个聊天机器人。

发布门槛：

- 材料/题干支持选词或选择片段；
- 岸岸入口携带题目、材料、当前选项、用时、信心和排除轨迹；
- 岸岸提出的“加入复练、记录错因、调整计划”等动作必须先预览再执行；
- 执行后有可核对的结果回执；
- 上下文权限与画像写入边界必须显式展示。

### UX-P0-05：每日结算和复盘完成态“看起来完成，实际没闭环”

每日结算当前主要是只读总结，而 Design File 已表达：

- 未完成任务如何处理；
- 移到哪一天；
- 明天第一项任务是什么；
- 用户如何确认这些变化。

错题复盘完成态当前也缺少设计稿里的关键动作：

- 生成或查看知识卡；
- 立即做两道验证题；
- 安排下一次复测；
- 明确本次画像是否更新。

这类问题比空白页更危险，因为页面视觉上像“已完成”，用户却没有完成真实决策。

### UX-P0-06：申论三屏交付没有按 Design File 落地

Design File 将申论拆成三个聚焦任务：

- 写作；
- 材料阅读；
- 批改复盘。

当前实现：

- `essay-task/index.wxml` 为 654 行；
- `essay-task/index.wxss` 为 1,234 行；
- 单页承担材料、找点、提纲、作答、改写、誊抄和复盘；
- `essay-material` 仍是旧通用工作台，缺少选中、标注、加入提纲等交互；
- `essay-review` 仍是旧通用工作台，缺少 Design File 的批改结构和下一步动作；
- `essay-compose`、`essay-rewrite`、`essay-evidence` 没有本版 Figma 基线；
- 长答案输入只改内存状态，`markDraftChanged()` 当前为空实现，退出或异常时有真实丢稿风险。

发布门槛：

- 以材料阅读、写作和复盘三个用户任务重新收口；
- 长答案必须有真实草稿持久化、恢复时间和保存状态；
- 材料标注能进入提纲或证据篮；
- 批改结果能回到原文定位并形成下一轮训练动作；
- 不用继续给现有巨型单页叠加补丁。

### UX-P0-07：拍照搜题的选择与答案状态缺少决策信息

当前拍照主路径已存在，但两个关键状态不能完成用户目的：

- 多候选结果只显示编号、相似度和通用提示，用户看不到足够题干、选项、年份或来源，无法判断选哪个；
- 参考答案页只告诉用户“详细解析会保存”，没有展示真正解析，用户不能当场完成学习。

此外：

- 当前使用 `wx.chooseMedia` 和 `wx.editImage`，并不是 Design File 表现的页面内相机和裁剪；
- 这是可以讨论的微信平台适配，但必须作为明确产品决定记录，不能称为一模一样复刻；
- 部分图标按钮缺少可读名称；
- 平板布局合同失败。

### UX-P0-08：建档结果主按钮文案与结果不一致

建档结果显示“开始双科起点诊断”，`record_baseline` 实际导航到今日页。

这是典型的“按钮有响应但交互错误”。用户会直接怀疑系统是否记录了自己的资料。

发布门槛：

- 按钮必须进入真正的双科起点诊断；
- 或者改为与真实落点完全一致的动作；
- 不能依赖用户自己在今日页寻找下一步。

### UX-P0-09：可见入口指向明确的未开放页面

“我的”页提供客服入口，但客服页明确显示二维码准备中、客服群暂未开放。

用户已经确认客服可以暂时占位，但商业产品的正确呈现应是：

- 未准备好时隐藏入口；
- 或展示真实可用的联系方式；
- 不能把“占位页”暴露给正式用户。

会员、支付、备份等已决定暂缓的能力也应遵循同一规则。

### UX-P0-10：平板端不能验收

平板布局测试结果：

- 5 项中 3 项通过；
- 岗位模块缺少约定的 `1180px` 内容宽度和多栏结构；
- 拍照搜题缺少约定的 `900px` 平板布局。

全局平板样式大多只是把页面限制在约 `720px` 居中，并不等同于平板适配。

申论长材料、题目与答案、岗位比较、拍照裁剪需要真正利用横向空间，而不是把手机页面放大后居中。

## 5. 全局视觉系统审计

### 5.1 设计语言方向是成立的

Design File 已形成明确方向：

- 冷灰画布与白色高圆角卡片；
- 石墨色文字；
- 靛蓝、紫色、粉色用于 AI 和关键能力表达；
- 安静、克制、留白充足；
- 今日、能力、岸岸、我的四个固定 Tab；
- AI 有科技感，但不使用廉价的全屏霓虹效果。

问题不在设计方向，而在运行时没有把这套方向固化成唯一工程系统。

### 5.2 令牌没有统一

Design File 精确令牌包括：

- 画布：`#f7f9fc`
- 表面：`#ffffff`
- 主文字：`#101828`
- 次文字：`#364153`
- 弱文字：`#6a7282`
- 主色：`#615fff`
- 紫色：`#ad46ff`
- 粉色：`#f6339a`
- 青色：`#00d3f3`
- 警示：`#ff6900`

运行时对应值存在偏差，并在大量页面继续硬编码。结果是同一个“主按钮”“成功状态”“警告卡”在不同模块具有不同色相。

### 5.3 卡片、圆角和阴影失控

现状有：

- 77 种圆角表达；
- 123 种阴影表达；
- 全局 `.card` 多处重复定义；
- 平板样式甚至引入暖橙阴影，与冷静的 Design File 方向冲突。

这不是“细节微调”，而是组件语义缺失。应把圆角和阴影与组件级别绑定，例如：

- 页面主卡；
- 普通信息卡；
- 可点击列表项；
- 浮层；
- 底部操作面板。

### 5.4 字号缺少可用性下限

Design File 导出的部分微型文字只有 `18–22rpx`。这些值可以作为设计参考，但不能机械照搬：

- 底部 Tab 当前约 `20rpx`，实际阅读过小；
- 元数据和辅助说明在真机上容易失去可读性；
- 长材料阅读需要单独的正文、行高和字号调节体系。

设计权威不应覆盖基本可用性。应在不改变版式精神的前提下建立真机字号下限。

### 5.5 Logo 与素材没有同源

当前 `logo-design-file.png` 是 88×88 的渐变栅格图；Figma 源码使用黑色线性脑形 SVG，并在白色圆角方块中叠加轻微渐变。

用户此前已经明确指出 Logo 不对。本问题不能再通过“重新画一个相似 Logo”处理，应直接建立：

- Figma 节点；
- 导出素材；
- 小程序文件；
- 使用页面；
- 哈希或版本号

之间的一对一映射。

## 7. 四个主 Tab 的 UX 审计

### 7.1 今日

优点：

- 信息层级总体接近 Design File；
- 今日任务、天气和开始学习入口容易找到；
- 天气只展示卡片符合当前决定，不需要再进入“来源”页面。

问题：

- 控制器已生成 `capacityMessage`，WXML 没有展示，用户看不到重排、冲突和保存结果；
- 岗位未发布时只告诉用户等待正式职位表，没有提供此前确认的历史趋势和大概分数定位；
- 全局 `.page` 的底部留白规则也作用于部分非 Tab 页面，容易制造大块无意义空白；
- 进入下层页面后视觉语言不连续。

### 7.2 能力

优点：

- 能力雷达、模块状态、趋势和岸岸入口的总体结构成立；
- 已说明综合指数不等同于卷面分。

问题：

- 雷达值目前主要由正确率驱动，与“正确率、用时、稳定掌握、复测”的文案不完全一致；
- 模块和错因下钻进入无 Figma 基线的旧页面；
- “查看怎么算的”没有形成统一、清楚、可返回的证据解释模式；
- 视觉仍混用旧橙色和硬编码颜色。

### 7.3 岸岸

优点：

- 没有退化成普通聊天气泡；
- 总控台、洞察、建议、行动预览和执行回执的方向正确；
- 已具备成为全局智能入口的基础结构。

问题：

- 返回岸岸时基础画像和今日上下文可能没有同步刷新；
- 做题中、材料阅读中无法携带选中内容进入岸岸；
- 工具按钮的命名承诺超过实际内容；
- 岸岸建议和各模块状态之间尚未形成统一动作协议。

建议把岸岸动作统一成四段：

1. 读取当前上下文；
2. 解释与建议；
3. 展示将要修改的对象；
4. 用户确认后执行，并返回可核对结果。

### 7.4 我的

优点：

- 个人资料、数据、设置和服务的总体分区清楚；
- 昵称编辑已存在。

问题：

- 头像仍是首字母和渐变样式，不是此前确认的微信头像选择；
- “申论记录”和“模考成绩”都进入同一个通用报告中心；
- “数据与隐私”“导出”“删除”都进入同一页面，但没有明确锚点；
- “授权管理”只进入消息通知设置，名称与范围不一致；
- 客服入口当前通向未开放页面；
- 部分接口失败时会把未知数据表现成“待补充”，用户无法区分“未填写”和“读取失败”。

## 8. 28 个无 Design File 基线的页面

### 8.1 应在发布前补设计或并入正式流程

| 类别 | 页面 |
| --- | --- |
| 模考 | `mock-exam`、`mock-report` |
| 用户设置 | `study-preference`、`privacy`、`profile/qualification`、`notification-settings` |
| 岗位 | `positions/briefing` |
| 行测 | `xingce-task-intro`、`xingce-mastery`、`ability-module`、`error-pattern` |
| 报告 | `report-center`、`external-report`、`report-overview`、`global-report` |
| 申论 | `essay-compose`、`essay-rewrite`、`essay-evidence` |
| 学习资料 | `learning-packets`、`answer-ingestion` |

这些页面是用户会从主要路径进入的正式页面，不能继续用旧模板作为交付结果。

### 8.2 应确认是否仍需要独立页面

- `retake`
- `plan-history`

如果其任务能够被能力页、周计划或报告页自然承载，应合并信息架构，而不是为了保留旧代码继续保留入口。

### 8.3 当前应隐藏

- `membership`：冷启动阶段已确认暂时免费、不限制；
- `support`：真实客服渠道未准备好；
- `community-draft`
- `community-structure`
- `community-trial`
- `community-contributions`

社区类页面已有代码不等于当前产品需要开放。未确认产品边界前不应让用户进入。

## 9. 关键交互链路审计

### 9.1 建档链路

整体步骤已经比旧版本清楚：

- 普通工作经历与服务基层项目已分开；
- 学习时间改成小时表达；
- 支持 0.5 小时步进；
- 在职和全职预设已存在。

仍需解决：

- 能力起点页缺少与其他建档步骤一致的暂存退出；
- 结果页主动作跳错；
- 建档后必须明确给出“接下来做什么”和系统将怎样使用资料。

### 9.2 岗位决策链路

正确目标应是：

1. 先判断资格；
2. 再按专业、地区和其他条件筛选；
3. 展示历史趋势和证据；
4. 解释为什么推荐；
5. 用户确认主目标。

当前搜索和详情存在，但：

- 职位未发布状态没有提前定位价值；
- 省市是自由输入，不利于附近地区推导；
- 推荐结果没有按专业优势、分数友好、邻近地区等决策理由组织；
- 三岗位手机横向比较的信息负担较高。

### 9.3 行测做题链路

现有能力较完整：

- 共享材料；
- 题号；
- 计时和暂停；
- 草稿；
- 信心；
- 排除轨迹；
- 自动保存；
- MyScript 数学手写；
- 交卷与复盘。

主要问题不是功能少，而是交互组织：

- 顶部工具触控面积约 58rpx，低于舒适触控目标；
- 工具入口太集中，但“岸岸”反而没有真正进入上下文；
- 选项主要使用可点击 `view`，缺少按钮语义；
- 复盘表单信息过多，应按“事实—原因—行动”逐层展开。

### 9.4 拍照搜题链路

正确目标应是：

1. 获取照片；
2. 用户裁剪；
3. 确认识别内容；
4. 匹配已有题目；
5. 展示解析；
6. 明确是否以及如何记入学习画像。

当前最大问题集中在第 4、5 步。没有可区分候选和即时解析，前面的拍照、裁剪和 OCR 都无法转化为学习价值。

### 9.5 申论链路

正确目标不是“把所有申论工具塞进一页”，而是让用户始终知道当前在做：

- 读材料；
- 找依据；
- 组织答案；
- 完成写作；
- 看批改；
- 形成下一次改进。

当前巨型单页把状态能力做得很多，但增加了定位成本、状态复杂度和维护风险。应按 Design File 的三个聚焦页面重组，不再继续扩大单页。

### 9.6 私人资料库链路

当前实现中的正确边界应保留：

- 资料只供本人检索；
- 不用于训练基础模型；
- 不跨账号复用；
- 上传不代表学会；
- 只有真实作答或用户明确确认的行为才能影响能力画像。

Figma 中以下文案不可直接搬入生产：

- “岸岸已完全掌握”；
- “计入能力画像”；
- “自动关联错题”；
- 把资料上传状态表达为用户已掌握。

应保留视觉结构，重写为真实处理状态和可验证动作。

## 10. 触控、可访问性与反馈

### 10.1 点击语义

代码中至少存在：

- 444 个按钮标签；
- 56 个使用 `bindtap`/`catchtap` 的可点击 `view`；
- 其中约 40 个没有角色或可访问性语义。

这会影响：

- 辅助功能识别；
- 自动化测试稳定性；
- 交互状态统一；
- 后续组件维护。

应优先把用户动作改为语义按钮；确实需要使用 `view` 时，补齐角色、标签和选中状态。

### 10.2 触控反馈

只有少量按钮显式声明 `hover-class`。部分页面使用 `:active`，微信原生按钮也可能提供默认反馈，因此不能简单说“完全没有反馈”。

真正的问题是没有统一合同：

- 哪些卡片可点击；
- 按下时如何反馈；
- 禁用、加载、成功和失败如何表现；
- 连续点击是否会重复提交。

### 10.3 底部 Tab

当前自定义 Tab：

- 使用可点击 `view`；
- 缺少 Tab 角色；
- 缺少 `aria-selected`；
- 标签字号约 `20rpx`，真机偏小。

应补齐语义和可读性，但不改变 Design File 的四栏结构。

### 10.4 图标按钮

返回、关闭、相机快门和工具栏中仍有只显示图标、没有可读名称的按钮。图标“看起来懂”不能替代语义标签。

## 11. 动效审计

当前存在约 19 处动画或关键帧表达，包括：

- 0.7 秒的入场动画；
- 无限 shimmer；
- 无限 pulse；
- 多套不同缓动和时长。

当前没有：

- `prefers-reduced-motion`；
- 统一动效令牌；
- 明确区分页面转场、加载、成功反馈和 AI 状态。

建议：

- 动效用于解释状态变化，不用于持续装饰；
- AI 可以具有光感和渐变，但避免所有卡片都“呼吸”；
- 无限动画只保留给真实进行中的任务；
- 页面主体入场缩短；
- 为减少动态效果的用户提供静态表现。

## 12. 平板与响应式

平板不能只依赖 `max-width` 居中。

应该使用平板空间的场景：

- 申论：左侧材料，右侧提纲/作答；
- 行测长材料：材料与题目/答案分栏；
- 岗位比较：固定行标签，横向比较候选；
- 拍照搜题：左侧图片与裁剪，右侧识别和结果；
- 私人资料库：目录与正文分栏。

暂时不应为了平板修改 Design File 手机版布局；应补独立响应式规则，并把手机、窄平板、宽平板作为三个正式验收档位。

## 13. 文案与信息表达

### 13.1 工程文案仍会泄漏给用户

需要全局清理的表达类型：

- 服务端目标版本；
- 规则版本；
- Request ID 长期占据页面主体；
- “暂无可用分差”但不给下一步；
- “服务暂时无法完成请求”而不说明用户能做什么；
- 原始英文状态值，例如申论批改里的 `severity`。

Request ID 可以保留在“查看详情/复制诊断信息”中，不应成为普通用户的主信息。

### 13.2 错误状态必须可行动

错误页不应只提供“重试”。需要根据场景回答：

- 用户的数据是否已经保存；
- 是否可以退出；
- 是否需要重新登录；
- 是否因为资料不完整；
- 下一步去哪里补；
- 重试会不会重复提交。

这不是降级兜底，而是正式产品状态。

### 13.3 未知不能伪装成未填写

接口读取失败时不能把字段显示成“待补充”，否则用户会以为自己的资料被清空。至少区分：

- 尚未填写；
- 正在读取；
- 读取失败；
- 数据已过期。

## 14. Design File 中不应直接复制的内容

“忠实接入 Design File”不等于复制所有原型代码。

以下内容应明确排除：

- 手机外壳、灵动岛、状态栏和微信胶囊的静态仿制；
- 只用于 Figma 演示的固定假数据；
- 私人资料库里的 `ViewSwitcher` 原型控制器；
- 把上传资料表述为“已掌握”或直接写入画像；
- 不符合真机可读性的微型字号；
- 没有错误、加载、冲突、权限、键盘和响应式状态的理想路径假设。

以下差异需要产品明确接受并记录：

- 拍照采用微信系统媒体选择，而不是页面内相机；
- 裁剪采用微信系统编辑，而不是页面内裁剪；
- 微信导航栏与胶囊安全区优先遵循真实设备几何。

## 15. 正确整改顺序

### 第一阶段：锁定视觉源

1. 把 Design File 令牌变成唯一运行时入口；
2. 建立 184 个设计素材到运行时素材的映射；
3. 先修 Logo、四个 Tab、导航、卡片、按钮、输入框和弹层；
4. 删除或隔离旧的青色、橙色和多套 `page-shell`；
5. 建立手机真机字号与触控下限。

完成标准：任何页面都不能再通过局部硬编码“模拟”Figma 风格。

### 第二阶段：完成关键用户任务

按优先级处理：

1. 登录同意；
2. 建档结果到起点诊断；
3. 今日容量反馈；
4. 岸岸做题上下文；
5. 每日结算；
6. 错题复盘完成态；
7. 拍照候选与解析；
8. 申论草稿、材料和批改；
9. 私人资料导入状态。

完成标准：每个页面都能回答“我现在在哪、为什么看到它、下一步做什么、动作会改变什么”。

### 第三阶段：处理 28 个无基线路由

对每个页面只能做三种决定：

- 补正式 Design File；
- 合并进已有正式页面；
- 从当前产品入口移除。

不再保留“以后也许有用，所以先挂着”的旧页面。

### 第四阶段：平板、动效与可访问性

1. 完成岗位和拍照现有失败合同；
2. 为申论、长材料和对比页面设计真正分栏；
3. 统一触控反馈；
4. 补语义、标签和选中状态；
5. 建立动效令牌与减少动态效果策略。

### 第五阶段：整体验收

最终验收不再逐页面手工碰运气，应同时具备：

- 58 个注册页面与产品范围一致；
- 所有用户可见路由都有设计来源；
- Design File 节点—素材—路由—组件可追踪；
- 每个关键流程有完整状态机测试；
- 手机与平板视觉回归；
- 真机逐链路验收；
- 不出现工程文案、假同意、假完成和无效入口；
- 岸岸能读取上下文、预览动作、执行动作并返回回执。

## 16. 给下一位前端模型的交接边界

下一位模型不能被授权“自由重画全项目”。应给它以下明确边界：

- Design File 是视觉权威；
- 业务边界和真实接口是语义权威；
- 不改后端合同，除非页面所需数据确实不存在并先提出合同变更；
- 不保留旧页面作为视觉兜底；
- 不重新画 Logo 和设计素材；
- 不复制 Figma 的设备外壳与原型控制器；
- 每次只交付一个完整用户任务，不按文件数量宣布完成；
- 未映射页面必须补设计、合并或隐藏，不能自行猜风格；
- 不以“编译通过”“按钮有 handler”作为 UI/UX 完成证明。

## 17. 最终判断

现在最需要的不是继续找一个更会画页面的模型，而是先把 Design File、运行时令牌、素材、路由和交互状态绑定成一套可验收的工程合同。

当前优势：

- Design File 的整体方向成熟；
- 四个主 Tab 的产品骨架成立；
- 行测运行时能力较丰富；
- 后端主体和数据边界比视觉层扎实。

当前主要风险：

- 设计稿与代码没有同源机制；
- 近一半注册路由无本版视觉基线；
- 申论、拍照、结算、复盘和岸岸上下文存在任务闭环缺口；
- 页面“看起来完成”容易掩盖用户实际上无法完成目的。

结论：

> **先统一视觉源并修完十项 UI/UX 发布阻断，再处理无基线路由，最后做平板与整体验收。完成这些之前，不应宣称 UI 已完整接入或可以发布。**
