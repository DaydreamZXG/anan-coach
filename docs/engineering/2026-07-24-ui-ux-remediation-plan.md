# 岸岸小程序 UI、UX 与交互修复计划

日期：2026-07-24  
计划性质：可执行修复路线；本文件不代表任何修复已经完成  
输入审计：

- [UI、UX 与交互深度审计](./2026-07-24-ui-ux-interaction-audit.md)
- [Figma 接入与生产功能审计](./2026-07-24-figma-production-audit.md)

## 1. 目标

将当前“部分页面接近 Design File、部分页面仍是旧工作台、部分动作只绑定不闭环”的小程序，收敛成一套：

- 视觉来源唯一；
- 页面来源可追踪；
- 用户任务能完成；
- 手机和平板均有正式布局；
- 岸岸能够贯穿学习上下文；
- 可以由自动化和真机验收共同证明

的可维护产品。

本计划不采用以下做法：

- 不删除现有 UI 后让模型重新自由发挥；
- 不继续在旧页面上叠加视觉补丁；
- 不把 Figma 原型代码直接当生产代码；
- 不为未设计页面临时猜一套风格；
- 不把“编译通过”“按钮有 handler”当作完成；
- 不暴露未开放的支付、会员、备份、客服或社区入口；
- 不以兜底页面掩盖缺失的正式流程。

### 2.2 已确认的产品边界

- Figma Design File 是排版、视觉和已画状态的权威；
- 真实业务边界、数据合同和用户已经确认的规则优先于原型文案；
- 岸岸不是普通聊天框，而是可以读取上下文、提出动作并操作全局的备考总控台；
- 天气卡只展示天气，不进入天气来源详情；
- 会员/支付、备份暂缓；
- 客服在真实二维码或渠道准备好前不开放；
- 私人资料不用于训练基础模型，上传不等于用户掌握，也不自动写入能力画像；
- 当前优先完成国考主产品，事业单位题库暂不混入当前产品边界；
- 产品按商业化质量建设，不做临时 MVP、降级兜底或一次性补丁。

### 2.3 尚需在对应批次确认

这些问题不阻塞第一批，但会阻塞对应页面完工：

1. 28 个无 Figma 基线路由最终选择“补设计、合并、隐藏”中的哪一种；
2. 拍照搜题是否正式接受微信系统选图和系统裁剪，而不是 Design File 的页面内相机/裁剪；
3. 岗位发布前历史趋势接口是否已提供完整数据；若没有，需先补正式合同；
4. 模考与报告究竟独立设计，还是并入现有做题与能力页面；
5. 申论旧路由如何兼容已有深链和未完成草稿。

## 3. 总体策略

修复按依赖闭环推进，不按“页面数量”推进。

```text
安全基线
   ↓
唯一视觉源与公共组件
   ↓
登录/建档/我的
   ↓
今日/计划/能力/岸岸
   ↓
行测/复盘/拍照
   ↓
岗位
   ↓
申论/私人资料
   ↓
无基线路由收口
   ↓
平板、无障碍、动效、真机与发布验收
```

设计验证以源码映射为主：

- Figma 节点 → 路由；
- Figma 令牌 → 运行时令牌；
- Figma 素材 → 小程序素材；
- Figma 状态 → 页面状态机；
- Figma 动作 → 真实命令或导航。

真机截图只用于最终视觉与设备 QA，不作为“猜测源码应该怎么写”的依据。

## 4. 测试节奏

为兼顾速度与可靠性，不在每改一个组件后跑完整测试。

### 编辑过程中

- 只运行受影响的 TypeScript 检查和目标测试；
- 不运行全仓视觉审计；
- 不因为旧模块的无关失败中断当前页面编辑。

### 每个修复单元结束

- 运行对应模块测试；
- 运行结构、路由、Design File 映射检查；
- 完成该单元的交互状态机测试；
- 检查变更范围没有越界。

### 每个整合波次结束

- 运行 `npm run typecheck`；
- 运行该波次全部相关 Vitest；
- 在微信开发者工具走一遍主链路；
- 检查工程文案、无效入口和旧视觉回流。

### 最终整体验收

- `npm test`；
- Design File 交付与来源校验；
- 58 路由产品范围校验；
- 手机和三档平板布局；
- 真机主链路；
- 登录、重登、后台恢复、错误、冲突和长输入恢复；
- 生产 API 联调。

## 5. 修复单元

## UX-00：保存当前基线

### 目标

在任何 UI 修复前，把当前 282 项混合改动变成可恢复、可比较的明确基线。

### 工作

1. 对未提交文件进行密钥和隐私信息扫描；
2. 核对删除文件是主动迁移而非误删；
3. 将 Figma 交付包、两份审计报告和当前真实功能代码纳入同一基线；
4. 提交一个只描述“修复前现状”的检查点；
5. 从该检查点创建 UI/UX 修复分支；
6. 记录 Design File SHA、当前提交和验证结果。

### 不做

- 不清理用户或其他模型的改动；
- 不重排页面；
- 不修改接口；
- 不把含密钥文件加入 Git。

### 完成标准

- 工作树可明确区分“修复前现状”和“后续修复”；
- 可一键回到当前版本；
- 密钥扫描没有未处理结果；
- Figma 交付校验仍为 8/45/45/184。

## UX-01：建立唯一视觉源

### 依赖

`UX-00`

### 目标

让 Design File 的令牌、素材和组件语义真正成为运行时代码权威。

### 主要文件范围

- `apps/wechat/design/figma-delivery/**`
- `apps/wechat/miniprogram/design-system/**`
- `apps/wechat/miniprogram/assets/**`
- `apps/wechat/miniprogram/app.wxss`
- `apps/wechat/miniprogram/custom-tab-bar/**`
- `apps/wechat/miniprogram/components/safe-top/**`
- 新增的 Design File 来源校验脚本和测试

### 工作

1. 将 `design-file.tokens.wxss` 接入唯一令牌入口；
2. 删除或隔离重复的 `.page`、`.card`、按钮和动效全局定义；
3. 建立组件级语义：
   - 页面画布；
   - 主卡片；
   - 信息卡；
   - 可点击列表；
   - 主/次/文字按钮；
   - 输入框；
   - 浮层与底部面板；
   - 空、加载、错误、冲突和处理状态；
4. 建立 Figma 素材映射表，至少包含节点、文件、哈希、用途和导出版本；
5. 用 Design File 的正式脑形 Logo 替换当前重新绘制的栅格 Logo；
6. 统一四栏 Tab、导航安全区、字号层级和触控反馈；
7. 移除平板样式中的暖橙阴影；
8. 新增源码级检查：
   - 已迁移页面禁止导入旧视觉壳；
   - 已迁移页面禁止新增未登记颜色；
   - 设计素材必须在映射表中；
   - 路由必须绑定 Design File 节点或明确处置决策。

### 完成标准

- 运行时只存在一套视觉令牌入口；
- Logo 和核心图标可追溯到 Design File；
- 四个 Tab、卡片、按钮和浮层不再依赖覆盖顺序决定样式；
- 公共组件支持默认、加载、空、错误、禁用、处理和冲突状态；
- 不改变任何业务接口和用户数据。

### 验收

```text
node apps/wechat/design/figma-delivery/scripts/validate-delivery.mjs
node apps/wechat/scripts/validate-structure.mjs
npm --prefix apps/wechat run typecheck
npx --prefix apps/wechat vitest run tests/design-file-core-tabs.test.ts tests/product-font.test.ts
```

- 学习偏好；
- 资格资料；
- 隐私；
- 通知设置；
- 客服入口。

### 工作

1. 登录：
   - 使用正式 Logo；
   - 协议和隐私可打开；
   - 同意状态真实可操作；
   - 登录按钮与同意状态一致；
2. 建档：
   - 保持普通工作经历与服务基层项目分离；
   - 保持小时制和 0.5 小时步进；
   - 给能力起点补齐暂存退出；
   - “开始双科起点诊断”进入真实诊断；

   - 接入微信昵称与头像选择；
   - 区分未填写、读取中、读取失败和已过期；

### 完成标准

- 新用户可从登录完整走到真实下一步；
- 老用户可修改相同资料；
- 不存在装饰性同意；
- 不存在主按钮文案和实际落点不一致；
- 读取失败不伪装成“待补充”；
- 所有可见账号页面视觉连续。

### 目标测试

- 登录控制器；
- 登录返回；
- 建档各步骤控制器与生命周期；
- 建档结果路由；
- 账户资料、退出与数据权利；
- 新增协议、头像和错误状态交互测试。

## UX-03：今日、计划、能力与岸岸总控台

### 依赖

`UX-02`

### 页面范围

- 今日；
- 任务依据；
- 周计划；
- 今日调整；
- 每日结算；
- 能力；
- 岸岸；
- 能力模块与错因模式。

### 工作

1. 今日：
   - 展示容量保存、重排、冲突和失败反馈；
   - 天气只作为摘要卡；
   - 明确当日主动作；
2. 周计划：
   - 恢复 Design File 的目标级层次；
   - 展示调整原因和对任务的真实影响；
3. 每日结算：
   - 处理未完成任务；
   - 确认迁移日期；
   - 确认明日第一任务；
   - 提交后展示真实回执；
4. 能力：
   - 统一能力指数的真实构成和解释；
   - 将模块、错因下钻迁入本版视觉；
   - “查看怎么算的”使用统一证据面板；
5. 岸岸：
   - 进入页面时刷新当前画像、计划和近期事件；
   - 建立统一 `AnanContext` 和 `AnanAction` 合同；
   - 所有高影响动作采用“建议—预览—确认—执行—回执”；
   - 不允许自由文本直接改变画像或计划。

### 可能的合同依赖

- 若每日结算缺任务迁移命令，先补正式后端合同；
- 若能力指数并非多证据综合，修正文案或补投影，不能假称综合；
- 岸岸动作必须调用已有领域 owner，不能创建第二套写路径。

### 完成标准

- 今日的每个状态变化对用户可见；
- 周计划和每日结算能完成真实决策；
- 能力解释有证据、有版本、有下一步；
- 岸岸成为总控台而非聊天页；
- 能力页进入下层页面时不再跳回旧视觉系统。

## UX-05：拍照搜题与外部学习

### 依赖

`UX-04`

### 页面范围

- 拍照搜题 11 个状态；
- 学习包；
- 答案收录；
- 相关私人资料引用。

### 开工前决策

从以下方案中正式选择一个：

- 微信系统选图 + 系统裁剪；
- 自定义页面内相机 + 页面内裁剪。

不得在代码里同时维护两套半成品。

### 工作

1. 相机/选图、裁剪、OCR、确认、匹配、解析、收录形成单一状态机；
2. OCR 确认页按题干、材料、选项和题型组织；
3. 多候选至少展示足以区分的题干片段、选项、年份/来源与匹配依据；
4. 答案页当场展示正式解析和证据来源；
5. 清楚说明：
   - 是否收录；
   - 收录到哪里；
   - 是否影响画像；
   - 用户如何撤销；
6. 无匹配、识别失败、权限拒绝、重新裁剪和重复收录都是正式状态；
7. 完成平板双栏布局。

### 合同停止条件

如果 API 不返回可区分候选或正式解析，停止 UI 实现并先扩展合同；禁止用通用占位文案伪装完成。

### 完成标准

- 用户可以判断候选；
- 用户可以当场学完；
- 收录与画像边界明确；
- 不出现“解析稍后保存”但当前没有解析；
- 平板合同通过。

## UX-06：岗位决策

### 依赖

`UX-03`

### 页面范围

- 岗位工作区；
- 搜索；
- 详情；
- 对比；
- 主目标；
- 考情说明；
- 资格资料关联。

### 工作

1. 正式职位表发布前：
   - 使用历史年份、专业、地区和相邻地区形成趋势定位；
   - 明确这是历史证据推断，不是当年录取保证；
2. 搜索条件使用受控地区层级，不再依赖自由输入；
3. 推荐结果按真实决策理由分组：
   - 专业优势；
   - 分数相对友好；
   - 邻近地区可选；
   - 其他硬条件；
4. “查看怎么算的”展示数据年份、样本、权重、缺失项和计算过程；
5. 手机端比较优先两岗，三岗使用可读的固定行标签或分步比较；
6. 平板使用多栏和固定比较标签；
7. 用户确认主目标后，今日和岸岸立即读取同一主目标事实。

### 合同停止条件

历史数据、专业权重或邻近地区关系缺失时，不在前端虚构结论；先补正式数据合同。

### 完成标准

- 职位未发布时页面仍能提供有证据的定位价值；
- 用户知道为什么推荐、数据来自哪一年、哪些信息尚不确定；
- 手机和平板都能完成比较；
- 主目标是唯一事实，不在多个页面各存一份。

## 6. 文件所有权与并行规则

在 `UX-01` 完成前禁止多人并行修改 UI，因为所有页面仍依赖共享令牌和全局类。

- `UX-06` 岗位；

- `app.json`、路由清单、全局令牌、生成 API、共享 TaskShell 和最终整合只由主整合任务修改；
- 两个任务不得同时改同一共享组件；
- 发现接口缺失时停止并提出合同变更，不在页面内伪造数据；
- 所有分支从同一个 `UX-01` 通过的基线开始。
