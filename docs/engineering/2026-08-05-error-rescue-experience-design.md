# 错题即时救场 — 产品设计草案

> 定位:考公搭子区别于普通刷题 App 的第一个 wow 体验。
> 主张:别的 App 告诉你"你做错了";考公搭子告诉你"你为什么错、怎么改、当场验证你会了"。
> 状态:草案,待产品负责人评审。所有零件已就绪(错因/方法卡/知识树/题库/中控大脑)。

---

## 一、普通产品 vs 考公搭子

```
普通产品: 做题 → 判对错 → 看解析 → 继续刷 → 下次同类题还错
考公搭子: 做题 → 判对错 → 识别"为什么错" → 推方法卡(当场看懂) → 重做同类题 → 验证会了 → 掌握状态更新
```

普通产品是"题库围着人转",考公搭子是"人围着目标转"。核心差异在**错题那一刻**:普通产品给"答案",考公搭子给"对症的解法"。

---

## 二、用户视角:一次"错题即时救场"的完整走查

### 场景:用户做错一道资料分析

**第 1 步:做题(普通)**
用户做一道"混合增长率"题,选错了。

**第 2 步:错因识别(考公搭子独有)**
系统不只说"选错了",而是:
> "这道题你错在**方法选择**——混合增长率的居中原则没掌握,不是算错,是思路没对上。"

(错因 agent 判断:不是 calculation_error 计算错,是 method_selection 方法不当)

**第 3 步:推方法卡(考公搭子独有)**
系统立刻推那张卡(472 张里恰好这张,通过知识树定位到"混合增长率"):
> 识别:问混合增长率,已知两部分增速求整体 → 方法:居中偏向基期大者 → 易错:别直接加权平均

30 秒看懂,不是一篇长解析,是一张"当场能用"的卡。

**第 4 步:当场重做(考公搭子独有)**
> "来,用这个方法再做一道同类题(从题库里选一道混合增长率)确认你懂了。"

用户做对了。

**第 5 步:验证 + 掌握更新**
> "对!混合增长率的掌握状态更新了。这类题下次你会了。"

错因、方法、掌握状态全部落库,影响明天的计划和中控大脑。

## 四、产品价值

### 用户为什么 wow
1. **第一次被"懂"**:不只是判对错,是知道你为什么错——从没 App 这样
2. **当场就会了**:错题 → 30秒看懂方法 → 当场重做对 → 信心回来了
3. **学习闭环**:错因落库 → 掌握更新 → 明天计划更准(中控大脑)

### 为什么普通产品做不到
- 需要错因识别(agent)——普通产品没有
- 需要方法卡(名师笔记提炼)——普通产品没有
- 需要把两者按知识树串起来——普通产品没有
- 这些是内容+AI的双重壁垒

## 五、实施建议(分三步,每步可验证)

### 步骤 1:错题即时救场(核心 wow)
打通:做题错 → 错因 → 方法卡 → 当场重做 → 验证
- 后端:新增"错题救场"流程(错因 + 匹配方法卡 + 同类题重做)
- 前端:做题结果页,错因+方法卡+重做按钮
- 验证:用户做错 → 看到方法卡 → 重做对

### 步骤 2:让"为什么"可见
岸岸/大脑解释"为什么今天学这个"(rationale 已能读,补展示)
- 用户问"为什么排这个" → 岸岸答"因为混合增长率是你的薄弱,距目标差X分"

### 步骤 3:入口 wow
从选岗生成个性化学习路径(目标 → 差距 → 每日计划 → 方法卡)
- 用户选岗 → 系统说"你的目标岗位需要X分,你差Y分,计划已按这个排"

## 六、待产品负责人确认

1. **救场的触发**:所有错题都救,还是只在"方法不当"类错因救?(建议:方法不当/知识缺口救场,粗心/时间压力不救)
2. **救场深度**:先文字方法卡,还是直接上交互式(卡 + 例题 + 当场练)?(建议:先文字,验证后再交互)
3. **重做题来源**:从题库按考点选同类题(推荐,5.5万题够)还是固定几道
4. **是否打断**:做题过程中错一题就弹救场,还是做完一组再集中救?(建议:做完一组,避免打断节奏)
