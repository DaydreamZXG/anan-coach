> 分支：`codex/ui-ux-remediation`

## 2. 总判决

当前产品不是“后端没写”，而是：

1. **事务型核心比预想扎实**：登录与用户隔离、建档、计划版本、行测提交与复盘、模考冻结判分、申论三模型批改、能力估计、私人知识库都有正式状态机、幂等键和审计事实。
2. **跨域学习闭环仍有断点**：练习事实没有稳定驱动下一次选题、计划、日结和学习大脑；因此暂时不能宣称“岸岸会随着用户练习持续变聪明”。
3. **上线运行面仍未闭合**：申论 worker 真实配置、生产备份与恢复证据、完整账号删除语义、开发工具公网暴露均未验收。
4. **不能立即对外发布**。可以继续内部真机验收，但生产放量前必须关闭本报告的上线阻断项。

## 4. 已验证的上线阻断

### B01（阶段 1 已关闭）· 计划会生成启动不了的行测任务

- 计划目标快照把内容闭合度固定为 `available`，没有验证目标模块是否真实有 3 道可供题目。
- 真正进入练习时才查询题库，供给不足会返回 503。
- 结果：用户在“今日”看到真实任务，点击后却无法开始。
- 责任边界：计划生成前必须消费同一个题目供给就绪合同，不能在页面做假兜底。
- 阶段 1 修复：计划与启动统一消费 learner-safe 三题供给门禁；不足三题时不发布行测任务。视觉资产、答案键与选项不一致也在计划前被排除。

### B02（阶段 1 已关闭）· 基础/专项训练跨天固定重复同一批题

- `real_attempt/service.py` 的 baseline / targeted 没有传用户全局历史排除。
- `real_attempt/repository.py` 按年份、出现次数、题号确定性排序后取前三题。
- 结果：同模块、同题库条件下会重复前三题，不是小概率问题。
- verification 只排除当前 mastery 链中的 `used_question_ids`，不排除其他训练链。
- 阶段 1 修复：baseline / targeted / verification 统一排除当前用户已冻结到题组或已形成 assessment 的全局历史；跨用户历史保持隔离。连续两组各三题不重复、供给耗尽后不再生成任务的回归已通过。

### B03 · 当前真实行测事实没有驱动下一份计划

- 当前作答写入 `learning.xingce_assessments`。
- 计划最弱模块和 calibration 知识点弱项仍读取旧 `learner.practice_answers`。
- 结果：“今天练了什么、错了什么”与“明天给什么任务”并非同一事实源。

### B04（阶段 1 已关闭）· 完成任务后日结会把它统计丢失

- 完成/放弃任务触发重排时，终态任务先从当前计划移除。
- 日结只汇总重排后的 `dashboard.tasks`。
- 结果：刚完成的任务可能从完成数、计划分钟和实际分钟同时消失。
- 阶段 1 修复：日结从当日最新执行版本精确回连其不可变任务快照，再合并当前无执行事实的开放任务；按 `work_item_key` 去重，不再从剩余 dashboard 反推历史。

### B05 · 学习大脑的模块速度读错数据路径

- 查询读取 `result_snapshot.questionElapsedSeconds`。
- 当前真实写入位于 `result_snapshot.timingEvidence.elapsedSeconds` / attempt timing evidence。
- 结果：模块平均用时长期为空，速度相关建议没有真实依据。

### B06（阶段 1 已关闭）· 模考多端轨迹冲突可能变成 500

- API 只验证 `eventSeq >= 1`，不验证等于服务端下一个序号。
- 数据库有 `(session_id, event_seq)` 唯一约束，但冲突没有统一转换成可重放的 409。
- 前端只对 409 执行 rebase。
- 结果：双设备或重放同序号可能抛 `IntegrityError`，本地队列无法恢复。
- 附带问题：`command_id` 数据库全局唯一，服务重放却按 `user_id + command_id` 查找，作用域不一致。
- 阶段 1 修复：服务严格校验 next sequence，已知唯一约束冲突转换为带 `expectedEventSeq / receivedEventSeq` 的标准 409；其他完整性错误不隐藏。迁移 `20260727_64` 将命令唯一作用域统一为 `(user_id, command_id)`。

### B07 · 往年成绩无法通过正式 API 成为“二战”证据

- 自报成绩与外部成绩单请求都没有 `examYear`。
- 服务统一写入当前 active release 年份。
- 二战识别只消费 `exam_year < target_exam_year` 的正式实考证据。
- 现有测试通过直接 seed 往年数据库记录绕过了真实录入路径。
- 结果：用户实际录入去年的成绩，系统仍可能认成今年，二战链不成立。

### B08 · 申论批改 worker 不能凭当前模板直接生产启动

- worker 入口与 systemd 单元在工作树中存在。
- 正式 grading release、价格卡、Grok/混元/仲裁配置及 checkpoint 加密配置没有完整生产值。
- 真实构造会 fail closed：`AI_ESSAY_GRADING_PLAN_RELEASE_ID is required and must be versioned`。
- 这是正确的失败方式，但意味着队列当前没有可证明的生产消费者。

### B09 · 数据导出/注销遗漏新领域，且外部清理完成语义偏早

- 导出/删除清单没有完整覆盖学习包、学习包绑定、答题卡录入、外部答案事实、iLink 等后来加入的领域。
- WeKnora 远端清理与本地投影级联删除存在竞态，可能先丢远端定位信息。
- iLink 账号删除可在对象删除队列排空前标记完成。
- 结果：页面显示“完成”时，不能证明所有个人数据已经导出或删除。

### B10（阶段 1 已关闭）· 岗位工作区可能丢失用户已确认的主目标

- `workspace()` 直接复用普通搜索并只取当前页。
- SQL 排序只看资格档、招录人数、岗位 ID；`is_primary_goal` 没有进入排序。
- 结果：主目标不在前 8 条时，工作区拿不到主目标，页面会误显示“尚未建立主目标”。
- 页面“已筛出 X 个可报岗位”使用全部 items 数量，但列表可能包含 `needs_confirmation` / `ineligible`，文案口径也不真实。
- 阶段 1 修复：工作区独立读取 confirmed primary goal，首屏固定置顶并从候选游标中排除；分页不重复、不丢候选，主目标变化会使旧游标失效。小程序计数只统计 `eligibilityStatus === "eligible"`。

### B11 · 生产安全与恢复仍缺外部证据

- `/coding-tools-mcp/*` 仍由生产 Caddy 反代本机工具端口，仓库内没有可证明的强认证。
- 工作树虽把发布脚本改成动态 Alembic 单头、前向迁移、worker 清单和备份门禁，但二次审查确认它缺少部署全局锁、冻结依赖制品、真实迁移失败演练、worker 稳定窗口和完整 unit reconciliation。
- 备份候选仍只写本机目录，`BACKUP_TARGET_ID` 只是清单文字；主机或磁盘故障时数据库与备份会一起丢，不能因此自动启用 timer。
- 进程内限流已复现两类绕过：同一 token 改 `Bearer` 大小写进入不同桶；桶满后制造新 key 驱逐受限桶，使旧 key 重新放行。重启、多进程、多主机也会重置或倍增额度。
- 数据权利 worker 固定 10 分钟把 `running` 重排，但通用 job 没有 heartbeat/lease；长任务仍在执行时可被第二个 worker 偷走并重复产生副作用。

### B12 · 图题供给与视觉指纹候选实现不能开闸

- `questionAssets` 只进入生成类型，行测/模考手写客户端合同和渲染层没有消费；原富文本路径又会剥掉 `<img>`。打开 `VISUAL_QUESTION_MODULES` 会出现“图题已入池、真机仍看不到图”的确定性断链。
- 新资产过滤接受任意 HTTP(S)，绕过既有 `public_question_asset_url` 的 HTTPS + 自有域 + 固定路径门禁；内网 IP、带凭据 URL 和不受控第三方域均可能进入题面。
- 指纹回填下载器允许任意外连和重定向，无 SSRF / DNS rebinding / 私网地址防护；完整读取响应后才检查 10 MB，图片解码前也没有像素上限。
- loader 没有 batch / active / rollback 发布语义，唯一键与运行时 policy 口径不完整；新 policy 可能冲突跳过却被后置守卫误判为成功。
- 当前 SQL 只用 exact hash 做视觉候选预筛，Hamming 只能重排文本召回或精确命中候选；页图与干净题图的裁剪域差存在时，并没有真正的近似视觉召回。
- dHash 没有质量/碰撞过滤；纯白、纯黑、纯灰图片均会产生同一个全零指纹。

结论：这些改动可保留为研究素材，但当前不得提交、不得拨开图题白名单，更不能据此宣称“拍照搜题视觉匹配已具备弹药”。

### B13 · 错因 Agent v2 → v3 没有版本化发布路径

- 当前 worker 严格要求队列任务的 definition / provider / prompt / schema 等于当前进程 release。
- 旧 v2 队列被 v3 worker 认领后会落入“unexpected + retryable”，不会退款、不会发布终止候选、不会推进 run/review；重试耗尽后仍遗留被占用权益。
- 激活/回滚脚本没有按 release 统计 queued / running / followup_required，也没有双版本 worker 或队列迁移门禁。
- 更严重的是跨版本追问：旧 v2 run 可在同一 `run_id` 下写入 v3 run version，却复用旧 `priorEvidence` 并跳过 v3 工具重跑。旧证据缺 `visualRequired / disputed`，默认 false 后会静默绕过新安全门禁。

结论：未实现版本化 dispatcher 前，当前 cause definition / prompt / schema / tool release 升级不得部署。一个 run 必须终身使用原 release，或显式建立新 run 并用新工具重新冻结证据；契约不匹配必须原子退款并进入明确终态。

### B14（本轮已关闭）· 行测毫秒时钟恢复会倒退

- 通用 `createTaskRuntime` 不接收、不恢复 `sessionElapsedMs`。
- 行测答案恢复不从已有 `actionEvents.atMs` 重建每题 `elapsedMs`，pending draft 合并也丢全局毫秒时钟。
- 新数学手写接口却把这些值声明成可跨证据比较的 active elapsed。
- 可达场景：已有动作 1337ms，服务端秒级回执为 1s；重建后立即操作会追加 1000ms，下一次 checkpoint 被后端单调性门禁拒绝。

本轮修复已同时覆盖服务端回执恢复、pending checkpoint、local draft merge、恢复后不经 TICK 立即操作和立即手写识别；没有在发请求前做局部 `Math.max` 补丁。新增回归用例以 1337ms 的非整秒轨迹验证恢复后立即改答不倒退，并验证 1500ms/1700ms 的待决草稿合并。相关 48 条定向测试与微信端 544 条全量测试已通过。

## 5. 重要但不宜擅自决定的产品口径

### D01 · 争议题是否影响能力画像

当前 `disputed` 已从错因模式聚合排除，但模块正确率仍消费 assessment。
需要明确二选一：

1. 争议未裁决期间完全不进入能力估计；或
2. 保留作答事实，只暂停错因归因，并在能力置信度中降权。

不能在 UI 承诺“不会影响能力画像”，因为当前代码做不到。

### D02 · 模考超时策略

前端到时自动交卷，服务端仍接受晚到提交，当前实际策略是“客户端计时、服务端优先保答案”。
若产品要求正式考试式硬截止，必须新增服务端 deadline 合同；不能只改页面计时器。

### D03 · 岗位推荐排序

已确认的产品口径是“专业优先，其次地区及其他条件；本地无岗时才考虑附近地区，并展示证据”。
当前实现只按资格档与招录人数排序，没有专业匹配等级、邻近地区关系和排序解释。需要单独设计可审计排序合同，不能偷偷改一个 `ORDER BY` 冒充完成。

### D04 · 题图资产域

工作树支持按模块白名单放开图题，但可选题图可能来自外部 HTTP(S) 地址。正式开闸前必须决定：

- 全部重托管到受控对象存储；或
- 建立明确域名许可、下载代理、内容校验与失效策略。

默认开关保持空是正确的，前端渲染和资产治理完成前不得放量。

## 6. 本轮修复与隔离结果

候选实现已经完成二次代码审查。阶段 0 将整批候选保存在命名隔离点
`quarantine: 2026-07-27 backend audit candidates before stage0`，再只恢复通过审查的独立修复：

1. 已恢复：数学手写请求附带 `sessionAtMs + questionElapsedMs` 活跃时钟；行测运行时从服务端答案事件、待决检查点和本地草稿恢复毫秒时钟，已关闭 B14。
2. 已恢复：学习大脑不再把全为“证据不足”的逐题候选退回会话错因并摊派到全部题。
3. OMR 空白/歧义答案允许以 `requiresCorrection=true` 进入人工纠错，确认前仍禁止写学习事实。
4. 笔记 App 导出按真实类型保存 `.md`，不再统一伪装成 `.pdf`。
5. 删除前端两个无后端合同且无运行时调用的孤儿方法：`/api/v2/goals/workspace`、`/api/v2/learning-profile`。
6. 已隔离：图题结构化资产、白名单供给和视觉指纹回填工具；二次审查发现前端未消费、资产域与指纹发布/召回存在 P0。
7. 已隔离：发布脚本、备份门禁、缺失 worker、崩溃任务回收与限流候选；二次审查已否决其“生产就绪”结论。
8. 应用默认 `REQUIRED_DATABASE_REVISION` 已从陈旧的 `20260721_53` 对齐当前唯一 Alembic head `20260727_64`；旧基线迁移回放夹具补齐后续迁移，新版社区贡献页验收不再要求已经删除的工程化旧文案。

二次审查对上述候选进一步分级：

- 已恢复并验证：学习大脑不回退全降级题、数学手写可选时钟、OMR 人工纠错、笔记真实扩展名、行测毫秒时钟恢复。
- 留在隔离点：append-only 新错因改判链、原始/确认公式的错因工具投影、`visual_not_supported / disputed` 状态，以及与它们绑定的错因 Agent v3 发布改动。它们必须和版本化 worker/旧队列迁移一起进入后续正式工作包，不能单独偷渡。
- 暂停执行：临时关闭 append-only 触发器并更新历史事实的 supersedes 回填 SQL；当前学习大脑已有决定链兜底，不执行脚本也能得到正确聚合。

## 9. 当前发布结论

- **内部真机验收：可以继续。**
- **小规模真实用户：暂不建议。**
- **公开上线：阻断。**

解除阻断的最低证据不是“页面能点通”，而是：

1. 本报告 B01–B13 的所有代码型阻断关闭或有明确产品决策；B14 保持回归测试覆盖；
2. 全量门禁通过；
3. 生产 worker 全部可构造并常驻；
4. 备份恢复演练有异机签名报告；
5. 数据导出与注销对新领域做真实样本核对；
6. Request ID 能在服务端日志中查到对应请求与 worker 链路。
