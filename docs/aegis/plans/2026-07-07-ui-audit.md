> 审计范围：`apps/ios/Gongkao/Gongkao/` 全部 SwiftUI 视图与数据层。

## 一、本轮已完成：接「明日政务预告」

**问题**：会话结束（今日任务全做完）原本只有一句静态文案「今日任务已完成，明天的计划会参考今天的表现。」——这是最强的留存钩子位置，却没用上真实数据。

**改动**（已编译通过 `BUILD SUCCEEDED`）：
- `AppModels.swift`：新增 `TomorrowPreview` / `TomorrowFocus` 解码模型（字段对齐后端 `/taskstream/tomorrow`）；AppState 增 `@Published var tomorrowPreview`，在 `loadInitialData` 内非致命拉取；`clearAuthSession` 同步清空。
- `StudyDeskView.swift`：① 把 iPad 教练面板「下一步」里的静态文案替换为真实的 `TomorrowPreviewCard`；② 新增 `TomorrowPreviewCard` 组件（内部可见，跨文件复用）。
- `FeatureViews.swift`：iPhone 完成态 `TodayCTABar` 的「全部完成」下方，追加同一张预告卡。

**设计纪律（学习优先）**：预告卡只聚焦「最弱模块补强 + 题量 + 分差(由 headline 自带)」，**不发放任何 cosmetic 奖励**——把今天的练习转化成「明天回来补弱项」的明确意图，而不是「解锁了新皮肤」这类 extrinsic bribe。

> 注：后端 `/tomorrow` 上一轮已部署上线（返回 401 验证路由存在）。iOS 需真实 Apple 登录 token 才能看到卡片，模拟器里若未登录则 `tomorrowPreview = nil`，自动回退到原静态文案，不崩。

## 二、审计发现（按优先级）

### 🔴 P0 — 双设计系统并存（最致命的「不像一个 App」）

项目里有**两套视觉语言**，且被同时混用：

| 调色板 | 定义位置 | 风格 | 使用方 |
|---|---|---|---|
| `GuzhuPalette` | `GuzhuDesignSystem.swift` | 古风：竹简纸底(米黄)、朱砂红、青瓷绿、赭石橙 | `StatusBarView`、`AppShellView`(iPad侧栏)、`GuzhuDesignSystem` 全部组件 |
| `DaziPalette` | `CoachComponents.swift` | 现代：纯白底、蓝紫渐变、圆角卡片 | `StudyDeskView`、`TodayView`、`FeedCardViews`、`CelebrationView`、`FeatureViews`、`CoachComponents` |

**后果**：同一个 App 里，顶栏是古风米黄 + 朱砂印章，往下翻却是现代白底 + 蓝紫渐变。用户会感觉「这是两个产品拼在一起」，彻底消解「治国」世界观的沉浸感——而这恰恰是你产品 thesis 的差异化护城河。

**建议**：**二选一，统一到 `GuzhuPalette` 古风**。`GuzhuPalette` 才是「治国」的差异点，`DaziPalette` 是通用 SaaS 皮，可替换、可抄袭。迁移成本：把 `DaziPalette.*` 引用逐文件替换为对应的 `GuzhuPalette.*`（颜色语义基本能一一映射：brand→cinnabar、positive→celadon、alert→cinnabar 暗调/cinnabar、paper→paper、card→card）。属于中等工作量但高回报，建议作为「让 UI 完美」的下一刀。

**次要**：即便不换 palette，`GuzhuPalette` 与 `DaziPalette` 都定义了 `paper/card/ink` 但**色值不同**（古风 paper 是米黄 0.93，现代 paper 是近白 0.98），背景一旦混用会出现「色块拼接」瑕疵。

### 🟠 P1 — 人设语气漂移（县令 vs 局长）

同一款产品，称呼自相矛盾：
- 「县令 / rankName」：`StatusBarView`、iPad 侧栏问候（`sidebarGreeting`）
- 「局长」：`CelebrationView`（`局长，漂亮！稳稳拿下`）、`TodayView.greeting`（`早，局长`）

产品是「治国·为官」，主语应是**县令/本官**一脉。「局长」是现代机关语境，跳戏。建议统一为「县令/本官/大人」一类古风称谓（可借 `GuzhuTerms` 做映射）。

### 🟠 P1 — 术语漂移（政务 vs 任务）

设计系统已内置 `GuzhuTerms.global`（`今日任务→今日政务`、`刷题→批阅奏折`…），但大量视图仍用现代词：
- `StudyDeskView`：`今日任务已全部完成`、`开始第 X 项`、`学习对象`
- `TodayCTABar`：`今日任务全部完成`
- `AppShellView` 侧栏：`今日政务 X 项 · 已批阅 Y 项`（已用政务，但和上面冲突）
- `StatusBarView` / iPad 侧栏：`今日政务`（已用政务）

建议：以「政务」为统一词，把 `StudyDeskView` / `TodayCTABar` 里的「任务」替换为 `GuzhuTerms.global("今日任务")` 之类，保证全 App 一个声。

### 🟡 P2 — 留存闭环缺口：归来推送未实现

`归来推送`（断更 1 天后本地通知，文案带考试倒计时 + 分差）在代码里完全没做（`UserNotifications` 框架虽链接但未调度）。这是「让用户玩几天」的另一个钩子，和明日预告成对。建议下一项做：纯前端本地通知，无需后端。

### 🟡 P2 — iPhone / iPad「今日」两套布局

`TodayView`(iPhone) 与 `StudyDeskView`(iPad) 是两套独立结构（侧栏、画布、教练面板各不相同）。功能一致但视觉/信息架构不统一。短期可接受（平板本就该信息密度更高），但长期应有一份共享的「今日信息层级规范」。

### 🟢 P3 — `ModuleHotbarView` 的 `selectedModule` 疑似未驱动任何可见行为

`AppShellView` 声明 `@State private var selectedModule` 并传给 `ModuleHotbarView`，但全局搜不到它被用于导航/筛选。若仅是装饰，建议要么接上（点模块跳转该模块练习），要么移除，避免「点了没反应」的死控件。

### 🟢 P3 — 惩罚机制已休眠（正面确认）

`fame / stamina / demerits` 仅在 `RankModels` 数据模型和 `StatusBarView` 的**预览假数据**里出现，**没有任何真实 UI 展示**；顶栏也已移除民心/精力。符合「MVP 休眠惩罚机制」的决定。
⚠️ 但仍建议做一次**后端安全排查**：确认 `censor_events` / `module_locks` / `fame` 衰减没有定时任务在自动触发（否则现有用户已被暗惩）。此排查之前被推迟，尚未执行。

## 三、做得好的地方（保留）

- `CelebrationView`：基于**真实正确率**分档文案，低分不撒谎（「难的地方你没绕开」），情绪价值而非虚假夸奖——符合学习优先原则。
- `GoalGapCard` / 顶栏分差：把「距上岸 X 分」做成常驻英雄指标，1:1 指向人生目标。
- 「搭子判断 / 这些安排从哪来」：每个推荐都标注数据出处，建立可信度。
- 暗色模式：两套 palette 都做了 light/dark 适配，基础无障碍到位。
- 新增 `TomorrowPreviewCard`：聚焦弱项补强、无 cosmetic 奖励，踩线正确。
