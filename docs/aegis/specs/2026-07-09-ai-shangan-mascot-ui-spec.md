## Product Decision

推荐方向：**公考搭子 / 上岸搭子**作为产品名，动物角色名为**鹿鸣**。

鹿鸣不是新功能，也不是独立聊天入口。它是 AI 上岸顾问的人格化表达：帮助用户理解岗位风险、接受分差现实、维持训练节奏，并在关键节点给出下一步动作。

选择鹿的原因：

1. “鹿”天然连接“录、路、禄”：录取之录、上岸之路、公职之禄，和考公语境贴合。
2. 鹿比猫更少撞车，避免和“上岸猫”类竞品形成名称/视觉近似。
3. 鹿的气质可以做得清醒、温和、可靠，不会把高压考试产品做成低幼宠物。
4. 可以继承现有古风色彩中的纸面、朱砂、青瓷，但不再用“县令/幕僚/官场惩罚”作为主叙事。

一句话产品感受：

> 鹿鸣已经根据我的条件、岗位数据和当前分数，给我排出一条上岸路。

## Competitive Signal

动物主题的价值不在“可爱”，而在“人格 + 习惯 + 记忆点”。

- 多邻国的 Duo 是品牌人格和学习习惯提醒的载体，不只是图标。
- 公考 AI 产品的用户核心诉求仍是诊断、选岗、计划、刷题、复盘，不是泛娱乐。
- 因此本产品不能直接学习猫/鸟/宠物陪伴，而要把动物角色放在“可信上岸顾问”的结构里。

结论：**专业决策在前，动物陪伴在后；报告像咨询产品，语气像有人陪你上岸。**

## Options Considered

### Option A：纯专业 AI 上岸顾问

只做报告、计划、图表和训练闭环，不做动物角色。

- 优点：可信、克制、适合高分人群和付费。
- 缺点：记忆点弱，留存和社交传播弱，容易像普通教育 SaaS。
- 结论：不选为主方向，但保留专业信息密度。

### Option B：强动物 IP 陪伴

首屏就是鹿鸣/猫/鸟，所有学习行为都拟人化。

- 优点：第一眼有差异，情绪价值强。
- 缺点：容易幼稚，冲淡岗位决策和分数预测的可信度。
- 结论：不选，考公是高压高投入决策，不能让用户觉得在玩儿童学习 App。

### Option C：AI 上岸方案为主，鹿鸣做陪伴和解释

首屏先给“上岸方案”：岗位组合、目标分、分差、风险、今日计划。鹿鸣作为报告中的顾问角色出现，负责一句话判断、提醒、鼓励、复盘解释。

- 优点：兼顾商业可信度、记忆点、留存和长期 IP。
- 缺点：需要严格控制视觉比例，防止角色抢走数据报告的主位。
- 结论：推荐并作为下一阶段实施目标。

## Experience Architecture

### 1. AI 问诊

用户先回答真实上岸决策需要的信息：学历、专业、身份、地区、政治面貌、基层年限、当前估分、每日可学时间、风险偏好。

UI 感受不是普通表单，而是“鹿鸣在收集能决定你能报什么、差多少、先练什么的条件”。但文案必须克制，不用大量解释性说明。

### 2. AI 上岸方案

问诊结束后首个结果页必须是报告，不是首页 dashboard。

报告核心顺序：

1. 鹿鸣一句话判断：你的上岸路径属于稳扎、拉分、冲刺或需重选。
2. 决策指标：当前分、决策目标分、分差、数据置信。
3. 岗位组合：稳妥、均衡、冲刺三组。
4. 数据依据：同岗历史分或上一年地区/专业预测样本。
5. 风险条件：资格、专业、政治面貌、基层、加试等未确认项。
6. 训练策略：今天先做什么，本周如何补差。
7. 主 CTA：生成今日上岸计划 / 开始第 1 项。

### 3. 今日上岸计划

首页不再问用户“你想打开什么功能”，而是展示鹿鸣已经排好的今日路径。

首屏必须回答：

- 目标是什么；
- 离目标差多少；
- 今天先做哪三件事；
- 为什么先做这些；
- 完成后计划会如何更新。

### 4. 执行与复盘

刷题、申论、错题、模考都是计划中的任务，不是并列功能入口。鹿鸣在任务结束后出现，给一句主判断和下一步动作。

复盘结构：

1. 这次暴露了什么错因。
2. 它影响哪个岗位/目标分。
3. 下一题或明天应该怎么调整。

### 5. 情绪和习惯系统

鹿鸣负责打卡、连续学习、低谷提醒和阶段庆祝，但不能羞辱、威胁或制造惩罚感。

允许：

- “今天先把最影响分差的一块补掉。”
- “这个岗位还能冲，但要把资料分析稳定到 80%。”
- “连续三天完成计划，说明节奏已经起来了。”

不允许：

- 官场惩罚、降级羞辱、威胁式催学。
- 把数据不足包装成 AI 确定判断。
- 用可爱文案盖住岗位风险。

## UI Direction

### Visual Identity

保留纸面、朱砂、青瓷、墨色等已有东方考试感，但降低“官场游戏”叙事。视觉关键词：

- 清醒；
- 温和；
- 有证据；
- 有陪伴；
- 不低幼；
- 不做单一红棕古风主题。

鹿鸣形象建议：

- 线条简洁，鹿角可做成“路线分叉 / 分数曲线”的隐喻。
- 表情状态少而准：`idle`、`thinking`、`confident`、`alert`、`celebrate`、`gentle`。
- 大多数页面只出现头像或半身，不要全屏遮挡数据。
- 训练执行页只做角标或反馈头图，不干扰题目阅读。

### Component Hierarchy

新增/改造组件建议：

- `LumingMascotView`：统一角色渲染，支持状态、尺寸、可访问性标签。
- `ShanganPlanHeader`：结果页首屏，鹿鸣 + 一句话结论 + 关键数字。
- `DecisionScorePanel`：当前分、目标分、分差、置信度。
- `PositionBucketBoard`：稳妥/均衡/冲刺岗位组合。
- `DecisionEvidencePanel`：同岗历史分或地区专业预测样本说明。
- `TodayRoadmapPanel`：今日 3 项主任务，绑定 planner/taskstream。
- `LumingBriefBubble`：每页最多一条主判断，不做满屏聊天气泡。

### Page Targets

#### Onboarding Target Step

当前 `OnboardingBaselineSteps.swift` 的目标页应从“推荐岗位列表”改成“AI 上岸方案预览”。

必须展示：

- 鹿鸣主判断；
- 当前总分；
- 决策目标分；
- 分差；
- 推荐岗位组合；
- 数据依据；
- 缺失条件；
- 生成今日计划 CTA。

#### Today Screen

首屏应从任务列表改成“今日上岸路线”。

必须展示：

- 目标岗位/地区；
- 距目标分差；
- 今日训练总时长；
- 第一项任务；
- 为什么先做；
- 完成后的计划更新预告。

#### Workbench

工作台承载生成对象：岗位报告、错因复盘、申论重写、模考分析、周计划。鹿鸣作为右侧或顶部上下文顾问，不作为一级 tab。

## Data and Contract Needs

已有可用基础：

- `GET /api/v1/position-decisions/recommendations`
- `decisionTargetScore`
- `decisionScoreBasis`
- `scoreGap`
- `recommendationBuckets`
- `unverifiedConditions`
- `nextActions`

下一步需要补齐：

1. iOS 把 `decisionScoreBasis` 公开展示，不只显示目标分。
2. 目标页选中岗位后，将岗位 ID、决策目标分、分差写入用户 profile / planner 输入。
3. planner/taskstream 接受 `positionDecision` 结果，生成第一天计划。
4. 首页展示的目标分差必须来自 profile + decision result，不能写死。
5. 鹿鸣话术必须基于结构化上下文生成或模板化拼接，不能空泛说“AI 已分析”。

## Implementation Slices

### Slice 4：鹿鸣上岸方案页

目标：把 onboarding 结果页改成有品牌人格、有证据、有行动的“AI 上岸方案”。

范围：

- 新增 `LumingMascotView` 或先用可维护的 SwiftUI 矢量占位组件。
- 重构 `PositionDecisionReport` 为上岸方案结构。
- 展示 `decisionScoreBasis` 的样本依据。
- 去掉目标页里像普通列表/表单的层级。
- 保持已有 `position_decision` API 不变。

验收：

- 用户不用懂后端字段，也能看懂“能报什么、差多少、为什么、今天做什么”。
- 鹿鸣可见，但不喧宾夺主。
- 没有伪造分数、伪造 AI 判断、伪造计划。
- iOS simulator build 通过。

### Slice 5：今日上岸路线首页

目标：让首页承接选岗决策，显示今日计划而不是功能入口。

范围：

- 今日页顶部改成目标/分差/计划主视觉。
- 引入鹿鸣一句话判断。
- 接入 taskstream/planner 当前已有能力；若 planner 缺字段，先补后端契约。
- 保留工作台和我的，不新增“鹿鸣”一级 tab。

验收：

- 打开 App 后第一屏明确是 AI 排好的今日路线。
- 今日任务能解释为什么服务于目标岗位。
- 训练入口只有一个主 CTA。

### Slice 6：角色资产与微文案系统

目标：把鹿鸣从一次性图形变成可持续维护的角色系统。

范围：

- 正式角色资产或可替换矢量组件。
- 状态枚举、使用场景、微文案规范。
- 统一旧的“幕僚/官场惩罚”文案退出规则。

验收：

- 新页面不再新增“幕僚/县令/降官/御史台”作为主叙事。
- 角色状态有统一 owner，避免每个页面手写一套。
- 深色模式、动态字体、可访问性标签可用。

## Non-Goals

- 不做全 App 一次性重皮。
- 不做独立宠物养成系统。
- 不做“鹿鸣”一级聊天 tab。
- 不替换后端岗位决策 owner。
- 不用假数据填充今日计划。
- 不把旧官场世界观立刻删除；先从主路径降级，后续按 owner 清理。
- 不承诺真实录取概率，只展示基于历史样本和当前估分的目标分与风险。

## Risks and Controls

| Risk | Control |
| --- | --- |
| 角色过可爱导致商业可信度下降 | 报告结构优先，鹿鸣只做判断和情绪承接 |
| 旧官场叙事与新顾问叙事冲突 | 新主路径禁用惩罚/幕僚称谓，旧模块逐步迁移 |
| UI 变成卡片堆叠 | 首屏只保留一个主判断、一个指标组、一个 CTA |
| 分数预测被误解成录取保证 | 明确展示 `decisionScoreBasis`、样本量、置信度 |
| 新增角色系统后组件散乱 | 统一 `LumingMascotView`、状态枚举和微文案 owner |

## Acceptance Criteria

规格被批准后，下一阶段实施必须满足：

- iOS onboarding 结果页第一屏呈现“AI 上岸方案”，不是普通岗位列表。
- 至少一个鹿鸣角色组件进入真实页面。
- 用户能在首屏看到当前分、目标分、分差、数据依据和下一步。
- 岗位推荐仍使用 `position_decision` 输出，不在 SwiftUI 里重新决策。
- 新 UI 不出现卡片套卡片、过度装饰、遮挡题干或按钮文字溢出。
- 新主路径不再强化“官场惩罚/幕僚”作为产品身份。
- 后端全量测试和 iOS simulator build 通过。
